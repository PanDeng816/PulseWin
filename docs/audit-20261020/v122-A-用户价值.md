# v1.22 用户价值主张（A · 重度使用者视角）

> 只读调研：`版本说明.md`（v1.21.7 至 v1.21.0，加 v1.20.5 / v1.20.4 / v1.20.2 / v1.14.x / v1.13.x 的历史反馈）、
> `docs\audit-20261020\services-audit.md` 与 `views-audit.md` 第 0 节及相关 P 项、`README.md` 功能章。
> 只新建本文件，未改任何源码。行号均来自本机实读。

## 结论：v1.22 只做这 3 件

| # | 用户能感知到什么 | 成本 | 主要证据 |
|---|---|---|---|
| **1** | 区间选一次，**整页**跟着走；写着"整个区间"的地方不再骗人 | **中**，2–3 天 | views P2-4 / P2-17；v1.21.1 反馈①、v1.21.5、v1.21.6 |
| **2** | 环停更时**说清原因**，并给一个能点的动作（重登/重试），不用重启 | **中**，1.5–2 天 | v1.20.5、v1.21.3；services P2-13 / P2-4；views P2-6 |
| **3** | 「最近对话」补上"其余 N 个会话"的合计，**今天这 2 亿谁烧的**能对上 | **小**，半天–1 天 | v1.21.4；`SpendWindow.xaml.cs:940-946` |

**排序逻辑**：v1.21.7 修的是"数会错"，v1.22 该修"数看不出、对不上、救不回"。
重度使用者每天只有三个动作——扫一眼环、问"今天怎么烧这么快"、问"和官方账对不对得上"。三件事各打一个。

## 1. 区间选一次，整页跟着走

**变化**：在顶部选「自定义 9/01~9/10」，或点热图下钻到某一天，下面的套餐 tab 徽标、套餐页 KPI、"本区间"数字跟着变；
凡写"整个区间"的地方，要么真覆盖全史，要么改写成"近 35 天"。顺带：拉宽窗口后曲线与热图立即重画（P2-3）。

**为什么现在做**

- **同一屏两套区间，代码里就摆着**：`Views\SpendWindow.xaml.cs:488` 用 `_span` 构建套餐索引，而总览、环比、导出用的是
  `EffectiveRange()`（`:468`、`:504`、`:2406`）——审计 views P2-4 定论"用户会把套餐页的数字当成本区间的数字"。
- **v1.21.5 把它从偶发变成了日常**：默认区间按用户要求改成"今天"后，凡下钻某天或选自定义，套餐页必然仍停在"今天"。
- **他为同类事连报三版**：v1.21.1 反馈①「本机记录永远显示近 30 天，不跟上方区间走」；v1.21.6「怎么还出现了本机比官方多，这不对」；
  v1.21.7 修 P0「调用次数双算」（近 35 天翻倍）。他的核对动作就是换区间对一遍，对不上就不信工具。
- **官方自己已经承认了一半**：v1.21.7 的"未修"清单列着 `RangeHourly` 只覆盖 35 天却标"整个区间累计"（views P2-17）。

**成本**：中，2–3 天。给 `ChannelUsageIndex` 加按日期区间的 `Build(ledger, from, to)`（P2-4 建议②），`RenderAll` 传 `EffectiveRange()`；
补 `RangeHourlyPartial`，时段分布标题/悬停改"近 35 天"；两处 `SizeChanged` 订阅（P2-3）。

**风险**：① 套餐 tab 按用量降序（v1.14.0 定的规则），区间一变顺序就变，正在看的套餐会换位甚至消失——选中态必须按 Key 记住；
② 「订阅额度」条本质是官方**当前**读数，不能跟历史区间，只能把标签从"本区间"改成"当前"（跟了就是造假数，这是取舍不是实现）；
③ 「全部」档下套餐页要按日区间过滤，得确认 `entries` 明细量级下不掉帧；④ 碰导出与四页渲染，回归面大。

## 2. 停更时说清原因，并给一个能点的动作

**变化**：某个环停更时，hover 卡里不只是一行「⚠ 数据 10.3 小时前 · 未能刷新」，而是
「Key 已过期 · 去重新登录」这类**一句原因 + 一个入口**；同步循环即便意外死掉也能自愈，不用重启。

**为什么现在做**

- **这是他被咬过两次的同一口**：v1.20.5"经常出现"、只能重启、日志里一片祥和；v1.21.3 又停 10.3 小时，根因（OpenCode Key 过期）
  只存在于 `Data\diagnostics.json` 的一行里。两次的体验都是"环停着，但我不知道为什么"。
- **rail 结构上就拿不到原因**：`SubData`（`SnapshotSource.cs:85-111`）只有 `FetchedAt`，没有错误字段，`IsStale` 只能算"多久没更新"。
  原因文本 `SourceStatus` 只在设置窗的数据源卡里（`SourceCard.cs:410-417`）——他不会为了看一句话去翻设置页。
- **自愈是缺的**：services P2-13 明确 `EnsureLoopRunning` 只由"手动刷新"调用；services P2-4 又让一把过期 Key 把整源误判成
  "需要重新登录"并静默 30 分钟——错误结论 + 静默期，正好凑成"看起来坏了、其实不知道该干嘛"。
- **同一个病灶在设置页也有**：加账号/贴 Key 失败时界面永远停在"正在验证 Key…"（views P2-6，`SourceCard.cs:111/230` 的 `async` lambda 无兜底）。

**成本**：中，1.5–2 天。快照加 `LastError`/`NeedsAuth` 两个字段 → 卡片在异常时多一行原因（正常时不出，符合 v1.21.2「能删尽删」）；
动作只做"跳到设置页该源卡片"（复用现成登录按钮），**不在 rail 上直接开模态登录窗**；`Loop` 的 `while` 内再包一层 catch + 1 秒重试；
`authFailure` 改为"最后一个候选的错误优先"；两处 `async` lambda 补 try/catch。

**风险**：① 卡片高度是算出来的（`CardRenderer.SubCard` 的 `StaleBlock` 一类常量），多一行会牵动卡片定位与 rail 尺寸；
② 登录窗是 WebView2 模态 + 跨进程互斥，从 rail 直接拉起会抢焦点、与"全屏自动隐藏"打架，所以我建议只做跳转；
③ 快照加字段要兼容旧文件（缺字段走默认）与 `_textCache` 的缓存键；④ 碰的是最核心的那条同步链路，"修坏"的代价比第 1、3 件大。

## 3. 「最近对话」补上"其余 N 个会话"的合计

**变化**：6 行下面多一行「其余 26 个会话 · 1.6 亿 tokens · ¥xx」，点开能看全部（或按用量排一刀）。
今天打开窗口，KPI 的 2 亿和下面的会话列表终于能对上。

**为什么现在做**

- **这是他自己点名要回来的**：v1.21.4「我的 PulseWin 里没有最近对话的 token 使用量了吗……显示最近 6 个对话的 token 使用量」。
- **但现在的 6 行对不上账**：`SpendLedger.cs:511-513` 按"最后活动时间"排序，`SpendWindow.xaml.cs:946` 取前 6；
  同文件注释直接写「这 6 行的合计与顶部的总量不必相等——两套口径,各自诚实」（`:940-941`）。
  v1.21.4 实测该区间 **32 个会话**，最贵的那几个很可能不在这 6 行里。
- **而且全窗口没有第二个入口**：v1.21.4 顺手删掉了「构成与明细」的会话分段与 `SessionList`，现在会话列表只剩这 6 行 + 导出 CSV。
  v1.21.4 刚写下"把常看的列表并进分段切换，等于把它藏起来"的教训，会话维度又回到了同一个坑。

**成本**：小，半天–1 天。加一行汇总（会话数 + tokens + 金额），点击弹全部/切排序；不新建窗口。

**风险**：① 总览会变高，v1.21.2 刚做过"空卡不占位 + 整页收紧"，别把页拉回去（可只在有剩余会话时才出现这一行）；
② 默认排序仍应"按最近"（用户原话是"最近 6 个"），"按用量"只能作为可选项，否则又逆着一次明确要求；
③ 合计必须说明"只含源库明细的会话"，否则与 KPI 的差额会变成第四个"对不上"。

## 不做什么

1. **外观、主题、液态玻璃回归**：v1.7.3 已移除液态玻璃；v1.21.2 的方向是"解释性小字能删尽删、更简洁"。增量视觉与既定方向相反，且一个数字都不会变准。
2. **新增数据源 / 给 BigModel 接官方接口**：BigModel 现在只有手填预算（v1.14.0），没有可读接口；v1.20.2 的教训是一个源的口径能错三分之一。v1.22 不再引入新口径。
3. **自动更新、静默替换 exe**：README 明说"只提示、不自动安装"，发布流程是人工换 exe + 留 `.old` 备份；静默替换会与单实例、DPAPI 凭据、WebView2 profile 打架。
4. **"AI 建议/该换套餐了"这类文案**：官方当日账未结算（v1.21.6）、BigModel 预算靠手填——给建议就是给假结论。本项目的原则一直是"不知道就显示 —"。
5. **记忆上次选的区间**：v1.21.5 明确要求"每次打开都是今天"，别逆着做"贴心"。
6. **把 `agg_hour` 保留期从 35 天拉到全史**（P2-17 的数据侧解法）：库体积和构建时间都要涨，而他只需要知道"这图是近 35 天"——一句文案够了。
7. **重构 `SpendWindow`（2590 行）、补单测、拆文件**：用户无感，交工程视角。

## 我还不确定的点

1. **订阅额度条到底算不算"该跟区间"**：它是官方实时池读数，跟历史就是假数；我倾向只改标签为"当前"。但用户可能读成"这工具区间还是没统一"——要不要在额度块加一句"这是现在的读数"，又与"能删尽删"打架。这是第 1 件里我唯一没有把握的取舍。
2. **第 3 件补合计行够不够**：他可能想直接浏览全部会话（那是一个新窗口，成本中）。建议 v1.22 先给合计 + "看全部/导出"，观察他是否还在点 CSV。
3. **卡片上放可点动作的手感**：点环=立即刷新、拖动=排序、右键=菜单，rail 交互已经很密。我倾向"只在异常时出现一行可点文字"，但真机手感读代码判断不了。
4. **停更原因的粒度**：要区分"Key 过期 / 网络不通 / 代理错 / 官方挂了"，现在 `SourceStatus.StatusText` 的措辞够不够准，我只核了设置页的映射（`SourceCard.cs:410-417`），没有逐通道验证。
5. **第 1 件会暴露官方口径的错位**：区间打通后，「官方口径对照」仍只有 24h/7d/30d 三档（v1.21.1 定的规则），自定义 9/01~9/10 只能被折成 30d 或 24h。这个错位我只能标出来，没有好解法——可能需要让自定义区间下的对照卡只显示"官方只提供 24h/7d/30d"并收起差值。
