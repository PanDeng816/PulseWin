# PulseWin v1.22 — 该做什么（B 视角：稳健性与可维护性）

- 评审基准：`v1.21.7` 源码。前提是 P0-1 与 P1 七条已修完（调用次数双算、两个并发字典、DSH 逐行容错、
  原子读写冲突、滑块重载、2FA 看门狗、文本缓存上限）。
- 本文只处理剩下的 17 条 Services P2 与 18 条 Views P2，以及"可测试性缺口要不要现在动"。
- 核对方式：只读。除两份审计外，实读了 `Diagnostics.cs`、`DshActivity.cs`、`UsageEngine.cs`、
  `ChannelUsage.cs`、`SpendWindow.xaml.cs`、`MainWindow.xaml.cs` 等现网代码，确认下列条目在 v1.21.7 里仍成立。
- 排序口径：**后果 × 发生概率 ÷ 成本**。后果只认两种：用户能看见的错数/卡顿，或程序不再自证的数据。

## 一、结论：v1.22 做这三件

| # | 做什么 | 动哪些文件 | 量级 | 为什么是它 |
|---|---|---|---|---|
| 1 | 同步循环的结构性自愈 + 唤醒兜底（P2-13/P2-14） | `Services\UsageEngine.cs` | ~15 行 / 0.5h | 唯一"用户看不见、程序也不会自己恢复"的失败模式 |
| 2 | 常驻周期性 IO 收口：诊断落盘出锁 + DSH 活动轮询降频（P2-15/P2-6） | `Diagnostics.cs`、`DshActivity.cs`、`Views\MainWindow.xaml.cs` | ~25 行 / 1.5h | 100% 概率的常驻开销，且是所有异常路径的放大器 |
| 3 | 让"界面声明的范围"等于"数据实际范围"（P2-7 + Views P2-17/P2-4） | `ChannelUsage.cs`、`SpendWindow.xaml.cs`、`SpendWindow.xaml` | ~25 行 / 2h | P2 里最后两处会让用户得出错误结论的地方 |

其余 P2 的处理见第三节（不修及理由）与第四节（顺手清单，总 ≤60 行）。可测试性改造本版不做，见第五节。

## 二、逐条论证

### 1. 同步循环的结构性自愈（`UsageEngine.cs:161-187` + `:120-135`）

**改什么**：`Loop` 的 `while` 体内再包一层 `try/catch (Exception)`，记一条诊断后 `await Task.Delay(1000, token)`
再继续；`RequestRefreshNow` 里 `if (_signal.CurrentCount == 0) _signal.Release();` 改成直接 `Release()` 并吞
`SemaphoreFullException`。

**现在的后果**：循环体只剩两处可能抛异常，`RunRoundAsync` 的异常边界是完整的，`_signal.WaitAsync` 不是。
Dispose 竞态下的 `ObjectDisposedException`、或者上面那个 check-then-act 撞出的 `SemaphoreFullException`，
都会让 `Task` 结束，而 `EnsureLoopRunning` 只有"手动刷新"一条触发路径。托盘程序一跑几周，症状是：
rail 永远停在"数据 20 分钟前 · 未能刷新"，没有弹窗，诊断里连一行错都没有（心跳是 `MainWindow.Tick` 写的，
与循环无关，照写），只能重启。v1.20.5 的现场就是这样。

**成本与风险**：纯增量 catch，成功路径一行不改，回归面只有同步循环。唯一风险是把真 bug 藏进 1 秒重试里，
用诊断带 `_loopTask.Status` 记一条即可观察。验证：真机断网 70 秒后点一次手动刷新，看"数据 X 分钟前"是否回落。

**判据**：只有本版正在重写同步骨架（单实例、多引擎之类）才可推迟，因为那会连带重写这 15 行。否则没有拖的理由：
成本低于一次回归测试，而后果是"常驻程序静默失效"。

### 2. 常驻周期性 IO 收口（`Diagnostics.cs:20-30`、`DshActivity.cs:143-156`、`MainWindow.xaml.cs:494-499`）

**改什么**：(a) `Note` 锁内只改 `Entries` 并取快照，`Flush` 移出锁，加 300ms 合并写；
(b) `RecentProjections` 加 2s 节流（`_lastScanAt` + 复用上次结果），`Tick` 仍每秒取结果。
两处都不改判定语义：DSH 的"在跑"本身有 5 分钟宽限，秒级精度本就不必要。

**现在的后果**：
- `Tick` 每秒在 UI 线程枚举 `~\.dsh\storages\session_projcache\sessions` 的 117 个文件做
  `GetLastWriteTimeUtc`，再对 10 分钟内写过的 ≤4 份约 20KB 投影做完整 `JsonDocument.Parse`。
  DSH 正在跑的时刻恰好就是呼吸动画需要顺滑的时刻，这是把最贵的线程用在最不需要精度的事上。
- `Diagnostics.Note` 在锁内同步整文件重写（temp + rename），调用方横跨 UI（60 秒心跳、登录窗、各 `catch`）
  与后台（同步失败、解析异常）。故障越密集，日志写得越频繁，锁持有越久，越可能把某一轮拖到
  2 分钟 watchdog 超时；这条链上没有背压，也没有丢弃策略。

**成本与风险**：两处都是降频与移锁，判定语义不变。唯一必须补的是"进程退出前最后几条不丢"（退出路径显式
Flush 一次），否则排查时最关键的尾部日志会缺。验证：重启后 `Data\diagnostics.json` 内容完整、最后一条是本次运行。

**判据**：改之前先量一次（把 `Poll()` 与一次 `Flush()` 的耗时打进诊断，看 P95）。若 SSD 上 `Poll` P95 < 3ms
且 `Flush` < 5ms，可以只做 (a)，把 (b) 推到 v1.23。不可拖的情形：出现"悬停/拖动偶发卡一下"的报障，
或诊断里同一分钟内出现 5 条以上 `Note`（说明已经在故障风暴里）。

### 3. 界面声明的范围 = 数据实际范围（`ChannelUsage.cs:159-161` + `SpendWindow.xaml.cs:488`、`:1925-1995`）

**改什么**：
- (a) `ChannelUsageIndex.Build` 增加 `(SpendLedger, DateTime from, DateTime to)` 重载，写法照抄同仓已有的
  `SpendSummary.Build`（`SpendLedger.cs:380-389`）；`SpendWindow.xaml.cs:488` 改传 `EffectiveRange()`，
  单日下钻同样走这条。旧 `Build(span)` 保留，`App.xaml.cs:659` 不受影响。
- (b) `ChannelUsage` 增加 `RangeHourlyPartial`（`span == All` 且仓库最早小时行晚于账本最早明细时为真），
  `:1993` 的"(整个区间累计)"与 `:1925` 的标题按它改成"近 35 天"。

**现在的后果**：
- (a) 选「自定义 9/1~9/10」后，总览所有数字切到该区间，同屏的套餐 tab 徽标、套餐页 KPI（标签明写"当前区间"）、
  额度条"本区间"仍是"今天"的数。用户看到的是同一个窗口里两套区间，最常见的反应是"统计算错了"，
  或者拿错数去对账。这是 `_customActive` 与 `_dayFilter` 完全没有进入渠道聚合的直接结果。
- (b) 选「全部」时 token 与金额是全史，下面是近 35 天的 24 小时分布，而 tooltip 写"整个区间累计"，
  峰谷占比也用它做分子分母。按错样本调时段，结论方向都可能是反的。

**成本与风险**：(a) 是 10 行机械改动，与已有 `SpendSummary.Build(from,to)` 同构，风险只在"全线区间"语义
（`SpendSpan.All` → `MinValue..now`）要逐字对齐；(b) 15 行加两处文案，不动数据。

**判据**：如果只有你一个人用、且只用"今天/7 天"、从不点自定义与"全部"，可以只做 (b) 的文案（约 5 行），
(a) 推到真有人用自定义区间时。只要这个窗口会给别人看，就必须做：同屏两套区间是用户最容易报成
"统计错了"的那一类 bug，而修法已经有现成范式。

## 三、明确不修的 P2（改了没收益，或风险更大）

| 条目 | 为什么不修 |
|---|---|
| P2-12 `AppSettings.Save` 加锁 | 读侧根本不进锁，只锁写侧等于零收益；真要解决必须 copy-on-write 全量快照，属设置模型重构 |
| P2-11 `Clone() => Sanitized()` | 两者语义不等价：`Sanitized` 会丢掉 `Id < 2` 的账号、夹取数值、清空货币，若 `Clone` 被当作"原样副本"就是静默改值。改为在类注释写死"加字段三处都要改"，成本 0 |
| P2-10 死代码 | 留着不产生运行成本。`ModelPrices.NormalizedVariants` 在计价链上（动它等于动钱数），`ChannelRegistry.Invalidate` 接上等于新增行为；只在该文件下次被改时删自己那一行 |
| P2-16 `UsageRepository` 全表读 | 当前天级 150 行、小时行 35 天。加 `WHERE` 会把"全史区间"的正确性风险引进来，换来的收益要到几年后才可测 |
| P2-8 工作区指纹 ±1 误配 | 本机只有 1 个工作区，无法证伪；此时改匹配算法只是换一种猜法。正确动作是加证据，见第四节末条 |
| Views P2-1 `HookHitTest` 接线 | 分层窗口命中原由 OS 按 alpha 决定，这段代码空转也没有可见后果。接到正确位置等于把行为从"系统兜底"改成"代码决定"，净风险为正，还得真机验证穿透 |
| Views P2-9 / P2-15 每帧克隆几何、热图 420 个 `Rectangle` | 每帧对象都会释放，没有累积（`_textCache` 那种只增的才是真问题，已修）；热图只在 `RenderAll` 时建，132px 小图、无卡顿报告。没有帧率证据前不动，改自绘要重做命中与 ToolTip |

| Views P2-8 `pixelsPerDip=96` | 结论本身未验证（审计也留了待确认）。先按 200% DPI 跑一次 `--card-shot` 对照，能测出 1px 再改 |
| Views P2-5 `RenderAll` 每次重读快照 | 当前数据量下每次几毫秒；读盘冲突已随 P1-7 收口。等 P95 > 100ms 再说 |
| Views P2-13 出图钩子的全局副作用 | 只在 `--ui-shot` 等进程里跑、跑完即退出。给不会发生的事加断言，是负收益 |
| Views P2-3 曲线/热图不随窗口重画 | 纯观感，且需要节流，排进去会挤掉第 3 件；等同版改渲染入口时顺手 10 行带上 |

## 五、可测试性缺口：v1.22 不动（结论）

**结论：不引入时钟/文件系统/网络接口，不建测试工程。**

理由：全仓只有一个 `PulseWin.csproj`，没有测试项目。此时把 `DateTime.Now`、`Environment.GetFolderPath`、
5 个静态 `HttpClient` 抽成接口，收益是"将来能写测试"，成本是动三条统计主链与五个进程级单例，而这正是
"钱数"所在的位置。v1.22 的三件事没有一件需要它。

**保留一条最小接缝**（可选，≤10 行）：`internal static Func<DateTime> Now` 用于 `SpendSummary.Range`/`Build`
与 `UsageRepository`，默认 `() => DateTime.Now`。它能让离屏命令复算任意历史区间，这是当前唯一缺的验证手段。

**什么条件下才动**：① 出现第二个"跨零点/月末"类 bug；② 要改 DSH 解析或仓库 schema（那时必须有 fixture，
`DshUsageStore` 根目录要可注入）；③ 有人愿意长期维护测试工程。三者之一成立再动，且仍按最小面推进。

## 六、建议实施顺序

1. **第 1 件**（0.5h，独立，先落）：纯保险，不与其它改动交织，先拿到"循环永不退出"的结构保证。
2. **顺手清单里的 1 行级五条**（P2-9/P2-4/P2-3/P2-2/P2-17）：一次编译验证，合计不到 10 行。
3. **第 3 件的 (a)**：与 (b) 文案同批，因为都要动 `SpendWindow`，且必须一次目测对照（自定义区间下总览与套餐页同口径）。
4. **第 2 件**：放最后，因为它是唯一"先量后改"的，实测数据可能说服你只做 (a)。
5. **验证口径**：`dotnet build -c Release` 零错误 → `publish` 单文件替换 → 重启看进程 Responding、
   `Data\` 无 `.tmp`、诊断无新错误 → 三项数字对照（今天/7 天/自定义区间下套餐页与总览一致、全部区间峰谷标签
   为"近 35 天"）→ 断网 70 秒后手动刷新能自愈。
6. **版本号**：做了第 3 件的 (a) 就是 v1.22.0（用户可感知：套餐页跟随自定义区间）；只做 1、2 与顺手清单则是
   v1.21.8（纯内部修复与文案）。

## 七、不确定项（需要实测或外部输入才能定）

- **第 2 件的开销量级**：`DshActivity.Poll` 与 `Diagnostics.Flush` 在本机的 P95 未测。这直接决定 (b) 是
  本版做还是推到 v1.23，建议改前先打一次耗时。
- **P2-8 误配概率**：本机 `orgs` 只有 1 个工作区，无法验证"两个工作区用量接近时取错第一个"。只能先按
  第四节最后一条加证据，跑一周再决定要不要动匹配算法。
- **Views P2-8 的 1px**：需要 200% DPI 下 `--card-shot` 与 `--ui-shot` 对照，当前无证据。
- **自定义区间的实际使用频率**：决定第 3 件做 (a) 还是只做 (b)。另外 `--spend` 类离屏命令目前没有
  `--from/--to`，改完仍只能开窗目测；想事后自证要先加这两个参数（与第五节的最小接缝一起做）。
